AI offers, PayPal checkout.

The café problem

Time and money, lost twice a day.

Guests queue to order and queue again to pay. By late afternoon pastries are left over. The owner knows an offer would help, but has no time to price it safely, and no one should let an AI change prices or move money.

⏳

Queues at the counter

Every table becomes its own counter: guests order and pay from their own phone.

🥐

Surplus at 4 pm

Café Copilot turns "sell the 8 croissants left before 4 pm, at most 10% off" into a checked draft.

🛡️

AI must not move money

The agent can read and draft only. People approve; PayPal takes the payment; the server verifies it.

How it works · real screens from the hosted demo

One flow, from offer to verified payment.

1

Café Copilot drafts the offer

  • The owner types one sentence. A Gemini agent with function calling uses six server tools: shop limits, stock, recent sales, validate, save draft, ask the owner.
  • The server computes the price (USD 4.50 → 4.05) and checks every limit. The agent has no tool to publish, charge or refund.
  • Every model call and tool result is stored as a trace.
paypal-pos.cashlessthailand.com · Café Copilot
Real hosted run: read_merchant_limits → read_catalog_stock → validate_campaign → save_campaign_draft.
2

The owner approves; the database holds the cap

  • Approve, then send the offer to the shop's screens.
  • A database trigger reserves offer units as bills are created, so the cap holds under concurrent orders (Reserved 1 · Left 7 while a bill is open).

On the hosted demo the table screens are labelled "simulated"; BitPOS Mini is existing hardware.

Approved campaign · screens · results
3

The guest orders at the table

  • Scan the table's code. No app, no sign-up.
  • The offer price is already applied; review the bill, confirm.
  • The bill is routed to that table only.
4

Pay with PayPal, proven by the server

  • The PayPal order (Orders v2, intent CAPTURE) is created from the server's locked quote, in cents. The browser never sends an amount.
  • JS SDK v6 popup → the server captures and verifies before the bill is PAID:

Payee

Single final capture

Signature-verified webhooks and a reconcile worker settle anything the browser misses. A timeout is "unknown", never "failed".

Also: order in Messenger

Just say what you want.

  • Write to the café's Facebook Page: "two iced lattes and a croissant".
  • The shop's AI builds the cart from the real menu; the server prices it as a normal table bill.
  • The reply carries a Pay with PayPal button to the same verified pay page, and a "Paid ✓" message after the capture is verified.
  • Meta webhooks are signature-verified (X-Hub-Signature-256) and deduplicated; message text is never stored.

Live-tested on 11 Nov 2026. The Meta app is in development mode: Messenger answers accounts added as app testers.

Built for things going wrong

Safe when things go wrong.

Rule broken?

The server refuses the proposal and Copilot asks the owner instead (e.g. ACTIVE_CAMPAIGN_EXISTS).

Retries & crashes

A PayPal-Request-Id per operation, one live checkout per bill, settlement in one transaction.

Late or duplicate money

Kept as RECOVERY for review, never dropped and never double-counted.
